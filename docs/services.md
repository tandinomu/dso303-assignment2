# Service documentation

This page lists every service in the architecture. For each one it shows what it does, why I picked it over a real alternative, how it is set up and what it connects to. The configuration values match `infra/main.yaml`.

## Edge layer

| Service | Role | Why over an alternative | Configuration | Connects to |
|---|---|---|---|---|
| **Amazon Route 53** | DNS for `exams.<uni-domain>` | Alias records point to CloudFront for free and resolve to edge IPs on their own. The university's own DNS server would be a single point of failure, and it can't alias to AWS resources | Public hosted zone; `A`/`AAAA` **alias** to the CloudFront distribution; health checks feed CloudWatch | CloudFront, ACM (DNS validation) |
| **Amazon CloudFront** | CDN and the single HTTPS entry point for the SPA and the API | It caches the app at edge locations, so the 3,000-student burst doesn't hit the origin. It also gives one domain for both the app and `/api/*`, so there is no CORS. Serving straight from an ALB would put all static traffic on the VPC with no edge caching | Two origins: S3 (Origin Access Control) and the ALB (`https-only` to `origin.<domain>`, adding the secret `X-Origin-Verify` header). Behaviours: `/*` → S3 with `CachingOptimized`; `/api/*` → ALB with `CachingDisabled` + `AllViewerExceptHostHeader`. HTTPS only, TLSv1.2_2021, HTTP/2+3, PriceClass_200 (includes India) | Route 53, WAF, ACM, S3 frontend, ALB |
| **AWS WAF** | Blocks common web attacks and floods | A managed web ACL with AWS rule groups needs no servers or upkeep. A self-run reverse proxy (e.g. ModSecurity on EC2) does. WAF also blocks bad traffic at the edge before it costs anything | Web ACL with `CLOUDFRONT` scope (created in us-east-1). Rules: `AWSManagedRulesCommonRuleSet`, `KnownBadInputs`, `AmazonIpReputationList`, and a rate-based rule of 2,000 requests per 5 min per IP | CloudFront |
| **AWS Certificate Manager (ACM)** | TLS certificates | The certificates are free and renew themselves. Buying certificates and renewing them by hand risks an outage if one expires mid-exam | Public certificate for `exams.<domain>` in us-east-1 (CloudFront requires this), DNS-validated through Route 53 | CloudFront, ALB |

## Frontend and authentication

| Service | Role | Why over an alternative | Configuration | Connects to |
|---|---|---|---|---|
| **Amazon S3 (frontend bucket)** | Hosts the built React single-page app | Static hosting is serverless, very cheap and durable. Running the frontend on EC2/Nginx would add servers to scale and patch, just for files that don't change between releases | Block Public Access ON. Only CloudFront can read it, through an OAC bucket policy. SSE-S3. Versioning on, so I can roll back a bad release | CloudFront, GitHub Actions (deploy) |
| **Amazon Cognito** | Role-based sign-in for students, tutors and admins | A managed user pool gives MFA, a password policy, account lockout and JWTs. Group membership comes out as a token claim. Writing our own login (password hashing, resets, MFA) is risky and slow. Cognito can also link to the university's SSO (SAML) later | User pool; groups `student`, `tutor`, `admin`; password min 12 characters; MFA optional (policy requires it for admin/tutor); app client with no secret (SPA) using SRP + refresh tokens; access token valid 60 min, refresh 1 day | Browser, API (JWT verification with JWKS) |

## API and compute (VPC)

| Service | Role | Why over an alternative | Configuration | Connects to |
|---|---|---|---|---|
| **Amazon VPC** | Private network across two AZs | It keeps the database and containers off the internet. Two AZs instead of one is what lets the platform survive an AZ failure | `10.0.0.0/16`; 6 subnets (public / private-app / private-data × 2 AZs, see `architecture/walkthroughs.md`); DNS hostnames on; VPC Flow Logs to CloudWatch | All in-VPC resources |
| **Internet Gateway** | Internet access for the public subnets | It is the only way for the ALB to receive traffic and for the NAT Gateways to reach out | Attached to the VPC; `0.0.0.0/0` route only in the public route table | ALB, NAT Gateways |
| **NAT Gateway (×2)** | Lets private tasks reach AWS APIs and the internet, while nothing on the internet can reach them | AWS manages it and keeps it highly available inside its AZ. A single NAT would be a cross-AZ single point of failure. A NAT EC2 instance needs patching and failover scripts | One per AZ, each with an Elastic IP; each private route table sends `0.0.0.0/0` to the NAT **in its own AZ** | Private app subnets, IGW |
| **VPC gateway endpoints (S3, DynamoDB)** | Private, free route to S3 and DynamoDB | Autosave traffic (100 writes/s) skips the NAT Gateway. That saves per-GB charges and removes a dependency. Interface endpoints would cost money every hour | Gateway endpoints attached to both private route tables | Fargate tasks, S3, DynamoDB |
| **Application Load Balancer** | Spreads API requests over the tasks in both AZs and runs health checks | It gives layer-7 path routing and health checks that work natively with ECS. API Gateway + Lambda was the alternative. But ALB + Fargate suits us better: the containers keep long-lived connections to Aurora (through RDS Proxy), and the cost stays predictable at a steady 300–500 users. An NLB has no HTTP routing | Internet-facing, in both public subnets; HTTPS listener (ACM certificate for `origin.<domain>`, TLS 1.3 policy). The security group allows only the CloudFront origin-facing prefix list. A listener rule forwards only requests that carry the secret `X-Origin-Verify` header, and anything else gets 403; target group type `ip`, health check `/health` every 10 s, 2 healthy / 2 unhealthy; deregistration delay 30 s; cross-zone on | CloudFront, Fargate tasks |
| **Amazon ECS on AWS Fargate** | Runs the API containers (Node.js) | There are no servers to patch or size, unlike EC2 Auto Scaling. It scales per task in seconds. For the main API it gives more control over connections and runtime than Lambda | Cluster with Container Insights; service with `desiredCount` 4 (2 per AZ), min 4, max 30; tasks 0.5 vCPU / 1 GB; **scheduled scaling** to min 12 (6 per AZ) thirty minutes before exams, following the exam timetable; target tracking at 60% CPU and 500 requests/target; spread across AZs; deployment circuit breaker with rollback | ALB, Aurora (via RDS Proxy), DynamoDB, S3, SQS, Secrets Manager, CloudWatch Logs |
| **Amazon ECR** | Stores the API container images | It is private, controlled by IAM and sits next to ECS. Docker Hub would add rate limits and a public dependency | Scan on push; immutable tags; lifecycle policy keeps the last 20 images | GitHub Actions, ECS |

## Data

| Service | Role | Why over an alternative | Configuration | Connects to |
|---|---|---|---|---|
| **Amazon Aurora PostgreSQL** | Relational data: users, courses, exams, questions, submissions, marks | Exams, enrolments and results are relational and need transactions and joins. Aurora keeps 6 copies of the data across 3 AZs and fails over faster (usually < 2 min) than standard RDS Multi-AZ. DynamoDB alone would make reports and joins awkward | Engine aurora-postgresql 16.9; Data API on; writer in AZ-a + reader in AZ-b (`db.r6g.large`); private data subnets only; storage encrypted with KMS; `rds.force_ssl=1`; backup retention 35 days + continuous PITR; deletion protection | Fargate (via RDS Proxy), Lambda (via Data API), Secrets Manager, AWS Backup |
| **Amazon RDS Proxy** | Connection pooling and faster failover | At peak, up to 30 Fargate tasks each hold their own connection pool. Together they would use up Aurora's connection limit. The proxy pools them and keeps connections open during failover | Targets the Aurora cluster; Secrets Manager credentials; TLS required; spread over both private data subnets; security group allows 5432 from the API only | Fargate, Aurora |
| **Amazon DynamoDB** | Stores in-progress exam attempts and the 30-second autosaves | An autosave is a single-key write at ~100/s, with bursts. DynamoDB on-demand scales at once, copies data across 3 AZs on its own and takes this load off Aurora. Writing autosaves to Aurora would make the busiest write path depend on one writer instance | Table `ExamAttempts`, key `attemptId`; **on-demand** capacity; PITR on (restore to any second in the last 35 days); KMS encryption; TTL removes drafts once the attempt is finalised to Aurora | Fargate API, marking Lambda, AWS Backup |
| **Amazon S3 (assignments bucket)** | Stores assignment files (PDF/ZIP ≤ 50 MB) for 5 years | It is cheaper and more durable (11 nines) than EBS or EFS. Presigned URLs keep 50 MB uploads off the API. Lifecycle rules handle the 5-year retention on their own | Block Public Access ON; default encryption **SSE-KMS** with bucket key; versioning on; bucket policy denies non-TLS requests; CORS allows PUT from the app domain only; EventBridge notifications on; **lifecycle**: Standard → Standard-IA at 90 days → Glacier Flexible Retrieval at 365 days → expire at 1,825 days (5 years); old versions expire after 30 days; incomplete multipart uploads aborted after 7 days | Browser (presigned PUT/GET), API, EventBridge, Lambda, KMS |

## Asynchronous processing

| Service | Role | Why over an alternative | Configuration | Connects to |
|---|---|---|---|---|
| **Amazon SQS** (marking + results-email queues) | Buffers auto-marking jobs and "results released" emails | It keeps slow work away from student requests. 3,000 submissions at the same moment just form a queue. SNS alone gives the consumer no buffering or retry control. Marking inside the API request would slow down submissions | Standard queues; visibility timeout 6× the Lambda timeout; KMS encryption; **dead-letter queue** after 3 receives; CloudWatch alarm when the DLQ has messages | API, upload Lambda, marking and notifier Lambdas |
| **AWS Lambda** (auto-mark, upload processor, results notifier) | Event-driven background jobs | You pay per job, and it scales with the queue depth on its own. Always-on workers on Fargate would cost money while idle for most of the year | Python 3.12; 256–512 MB; timeout 30–60 s; SQS batch size 10 with partial batch responses; reserved concurrency 50 for marking; reaches Aurora through the **RDS Data API** (HTTPS + IAM), so the functions need no VPC attachment and can't use up DB connections | SQS, EventBridge, S3, DynamoDB, Aurora (Data API), SNS, SES |
| **Amazon EventBridge** | Routes "object created" events from S3 to the upload processor | It filters on content (prefix `submissions/`) and makes it easy to add targets later (e.g. virus scanning). Plain S3 → Lambda notifications allow only one target per prefix | S3 bucket EventBridge integration on; rule on `Object Created` for the assignments bucket and prefix; retry policy of 24 h plus a DLQ | S3, upload Lambda |
| **Amazon SNS** (topic `tutor-notifications`) | Emails the tutor when a student submits an assignment (walkthrough 2) | One publish reaches every subscribed tutor, and SNS retries delivery itself. Tutors are a small, fixed group, so the one-time subscription confirmation is fine. SES would need a template and a recipient lookup for every upload, which is more work for a simple alert | Standard topic, KMS-encrypted; email subscription per tutor/course mailing list; the upload Lambda's role allows only `sns:Publish` on this topic | Upload Lambda, tutors' email |
| **Amazon SES** | Sends "results released" emails to students | It is built for high-volume, formatted email to thousands of people, with bounce and complaint handling. With SNS email, every one of the 8,000 students would have to confirm a subscription, and the emails can't be formatted. Running our own mail server isn't worth it | Verified domain identity with DKIM + SPF; configuration set with bounce/complaint events to CloudWatch; production access requested (out of the sandbox) | Notifier Lambda |

## Security, monitoring, backup and delivery

| Service | Role | Why over an alternative | Configuration | Connects to |
|---|---|---|---|---|
| **AWS KMS** | Encryption keys for data at rest | A customer-managed key logs every decrypt in CloudTrail and gives key rotation and key policies. AWS-owned keys give no control or visibility | One CMK, automatic yearly rotation, used by S3, Aurora, DynamoDB, SQS, Secrets Manager and backups; the key policy limits use to the app roles | S3, Aurora, DynamoDB, SQS, Backup |
| **AWS Secrets Manager** | Holds the database credentials and the CloudFront → ALB origin secret | It rotates secrets on its own, and IAM controls who reads them. Environment variables and plain SSM parameters don't rotate. Credentials never appear in code or the repository | Aurora master secret created by RDS (`ManageMasterUserPassword`) with rotation; ECS reads it through the task definition `secrets` field | Fargate, Lambda, RDS Proxy |
| **AWS IAM** | Least-privilege permissions | Each component gets its own role. For example, a compromised Lambda can't read the database secret. Shared access keys would let an attacker move sideways | Separate ECS task role, execution role and one role per Lambda; GitHub OIDC deploy role limited to the repository's `main` branch; no long-lived access keys | Every service |
| **Amazon CloudWatch** | Metrics, logs, alarms and dashboard | Every service here reports to it natively, so there is nothing extra to run. Prometheus/Grafana would mean hosting and looking after more infrastructure | Log groups (90-day retention) for ECS, Lambda and VPC Flow Logs; alarms: ALB 5xx > 1%, p95 latency > 1 s, ECS CPU > 80%, Aurora CPU > 75%, DLQ depth > 0, DynamoDB throttles > 0 → SNS → on-call email; dashboard for exam day; X-Ray tracing on the API | All services |
| **AWS CloudTrail** | Audit log of all API calls | We must show who changed what (marks, users) over the 5-year period. Our own audit logging would miss changes made outside the app | Multi-region trail; log file validation; logs to an encrypted S3 bucket, moved to Glacier at 90 days and kept 5 years | S3, KMS |
| **AWS Backup** | Central backups, kept 5 years | One policy covers Aurora and DynamoDB, and the vault enforces retention. The alternative is a separate snapshot script for each service | Backup plan: daily backups kept 35 days, monthly backups moved to cold storage and kept 5 years; vault encrypted with the KMS key (Vault Lock can be added to make it immutable); restore tested each term | Aurora, DynamoDB, KMS |
| **AWS CloudFormation** | Infrastructure as code (`infra/*.yaml`) | It is native to AWS, with no state file to store or lock (unlike Terraform). It detects drift and rolls back on its own when a deploy fails. Building in the console can't be repeated reliably | Stacks `exam-prod-waf` (us-east-1) and `exam-prod` (ap-south-1); parameters for environment and image tag; deletion protection on data resources | All services |
| **GitHub Actions** | CI/CD: test, build and deploy on every push to `main` | The code already lives on GitHub, it is free for student repos, and it uses short-lived OIDC credentials. CodePipeline would be one more service to set up for the same result | `.github/workflows/deploy.yml`: lint template → build and push the image to ECR → `cloudformation deploy` with the new image tag → sync the SPA to S3 → invalidate CloudFront; environment protection on `production` | GitHub, IAM OIDC role, ECR, CloudFormation, S3, CloudFront |
